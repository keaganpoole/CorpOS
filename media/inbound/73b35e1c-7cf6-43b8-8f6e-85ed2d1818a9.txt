# Task 1 — Fix Database Tab Variable Set Visibility

## Objective

In the Database tab of the Variables Panel, only show variable sets for tables that would actually have data available at runtime.

Do not show irrelevant or unrelated table variable sets.

## Core Rule

The available variable sets must be determined from:

- The trigger/action data path
- Previous node outputs
- Valid foreign key relationships between records

Do not show every table in the database.
Do not grey out irrelevant variable sets.
Hide irrelevant variable sets entirely.

## Ordering Rule

Show variable sets from bottom to top like this:

- Most foundational/parent record at the bottom
- More specific/related records above it
- Newly introduced tables from later nodes continue stacking above the existing variable sets

## Example 1

Scenario:

When a payment fails (trigger) > Create a payment (action)

The failed payment trigger should expose:

- The payment record from the trigger
- The person/customer record attached to that payment through the foreign key relationship

So when configuring the Create Payment action node, the Database tab should only show:

Bottom: people  
Above it: payments

## Example 2

Scenario:

When an appointment is completed (trigger) > Create a payment (action) > Call customer

The completed appointment trigger should expose:

- The appointment record
- The person/customer record attached to the appointment
- The service record attached to the appointment, if the appointment has a service foreign key

So when configuring the Create Payment action node, the Database tab should only show:

Bottom: people  
Above it: appointments  
Above that: services, if a linked service record exists

## Important Rules

- Only show variable sets that are actually reachable from current scenario runtime data.
- Reachability can come from the trigger, previous nodes, or valid foreign key relationships.
- Irrelevant tables must not appear at all.
- Do not show disabled/greyed-out irrelevant variable sets.

# Task 2 — Add Search Records Action

## Objective

Add a new Records action called:

Search Records

This action should allow the user to search records from a selected table, limit the number of returned records, and expose those records as structured variables for later nodes.

## 1. Records Action Menu

Inside the existing Records action button/menu, add:

Search Records

Selecting it should create a new action node in the Scenario Builder.

## 2. Search Records Node Form

The Search Records node configuration form should include:

### User ID

- Text input field
- Placed at the top of the form
- Used to scope which user’s records are queried

### Table

- Dropdown field
- Options should include available database tables, for example:
  - people
  - payments
  - appointments
  - services
- Use the same table/schema source already used by existing Records action nodes.

### Limit

- Number input
- Controls the maximum number of records returned when the node runs
- Prevent unlimited record fetching

## 3. Run Node Behavior

Allow the user to right-click the Search Records node and choose:

Run Node

When Run Node is selected:

- Execute the Search Records node using the selected table, limit, and User ID
- If User ID is provided:
  - Filter all queries by this User ID
  - This overrides the default session/user context for testing purposes
- If User ID is empty:
  - Fall back to the normal authenticated user/business/account context
- Do not fetch records globally across all users
- Return the results as structured JSON

## 4. Scenario Tab Variable Output

After the Search Records node runs successfully, show a new variable set in the Scenario tab of the Variables Panel called:

Search Records

This variable set should contain the records returned by the node.

Example structure:

Search Records

      id
      first_name
      last_name
      email
      phone
    1
      id
      first_name
      last_name
      email
      phone

Each returned record should be collapsible, similar to Make/Integromat bundle outputs.

The Search Records variable set must be extremely clean, structured, and visually consistent with the existing Variables Panel design.

### Requirements

- The output must feel native to the Variables Panel (not like a raw JSON dump)
- Maintain the same spacing, typography, and hierarchy used by existing variable sets

### Bundle Structure (Make/Integromat Style)

- Default state:

- Maintain consistent vertical rhythm between fields

### Structural Guides (Important)

- These lines should help users visually trace the structure of the data
- Do not make the UI feel cluttered — lines should enhance clarity, not dominate it

### Readability

- Long datasets must remain easy to scan
- Avoid cramming — prioritize spacing over density
- Ensure labels (field names) are clearly distinguishable from values

- Do not introduce new UI paradigms
- Extend the existing design system only
- The result should feel like a natural, polished extension of the current variable sets
